# BOT Point v4.1.0 — автономный worker

Web (gunicorn render_entry:app) и отдельный постоянно работающий worker (python render_worker.py) используют только собственную базу BOT Point. StaffFlow не запускает worker. Для production нужен **один** активный потребитель того же BOT_TOKEN: остановить локальный poll и второй Render-сервис, если они используют тот же токен. Не запускайте worker в Gunicorn и не используйте бесплатный засыпающий web как постоянный worker.

Worker: DATABASE_URL, BOT_TOKEN, CHAT_ID, THREAD_ID, BOT_POINTS_WORKER_ENABLED=1; API_ID, API_HASH, TELETHON_STRING_SESSION для истории; BOT_POINTS_AUTO_HISTORY_ENABLED=1 включает её каждые 15 минут. Сессия должна быть независимой, не одновременно использованной на другом сервере. Обработка истории и polling сериализованы, offset и статусы хранятся в DB. Google-цикл раз в минуту; общий PostgreSQL transaction advisory lock сериализует web и worker записи и восстановление pending job. Локальная SQLite использует threading.Lock. Потеря соединения с БД во время внешнего запроса остаётся неопределённой ситуацией: проверить журнал и таблицу.

**Безопасный первый запуск:** BOT_POINTS_WRITES_ENABLED=0 и BOT_POINTS_CLOUD_WRITES_CONFIRMED=0 и на web, и на worker. Сначала проверьте целевую тему и таблицу, загрузите историю, перенесите/сверьте прежний ledger sheet_message_applied / sheet_applied, проверьте unresolved manual pending/uncertain операции. Без сохранённого ledger старые сообщения могут быть повторно усреднены. После проверки можно установить обе переменные в 1 на обоих сервисах и включить автообновление в UI. Автоматически никакие секреты и реальные записи не меняются. Неподтверждённая ручная запись блокирует следующую запись до административного разбора; UI разрешения таких операций пока отсутствует.

Dashboard: /api/runtime-dashboard доступен только авторизованному администратору (существующая gateway_auth). Показатели по исходной дате отчёта, текущей очереди, уникальным партномерам в журнале выбранной таблицы с сегодняшним обновлением и зарегистрированным ошибкам. Не отображает содержимое секретов. Статус SSO «настроено» не означает проверенный реальный обмен. История не обнаруживает удаления сообщений; это отдельная задача. Автоматическое чтение истории использует существующий 30-дневный диапазон. Периодичность зависит от задержек Telegram/Google и доступности сети. Старые правила расчёта и ID сборки не меняются.
